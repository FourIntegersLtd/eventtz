# 0002 — Supabase Postgres, used as plain Postgres through SQLAlchemy 2.0 and Alembic

Status: accepted (2026-10-16). Revises the 2026-09-26 version ("Postgres on Railway"), which
supersedes "keep supabase-py" (2026-09-25). Source: OSCE Guide `platform-api` ADR 0013.

## Context
Every supabase-py `.table()` call is one HTTPS round trip to PostgREST. Pages that
make several sequential calls were measurably slow. PostgREST also cannot open a
multi-statement transaction or take a row lock, so atomic money writes needed
hand-written `.rpc()` functions. OSCE Guide already runs SQLAlchemy + Alembic on
psycopg 3; one stack across both projects was the deciding constraint.

The first version of this ADR also moved the data to a new Railway Postgres. That
meant an export/load/verify cut-over of every table and the auth hashes, and giving
up Supabase's backups, point-in-time recovery and dashboard. None of that is needed
to get rid of PostgREST: the slowness and the missing transactions come from the
client, not from where Postgres runs.

## Decision
- **The database stays the Supabase project's Postgres**, used as plain Postgres:
  `DATABASE_URL` → SQLAlchemy/psycopg. No supabase-py, no PostgREST, no Supabase
  Auth (ADR 0003). Railway hosts only compute (`api`, `worker`, `web`).
- **Connect through Supabase's session pooler** (Supavisor, IPv4, port 5432,
  `postgres.<project-ref>` user, `sslmode=require`). The direct host is IPv6-only and
  Railway has no outbound IPv6. The transaction pooler (6543) is out: procrastinate
  needs a real session for LISTEN/NOTIFY and advisory locks, and psycopg prepares
  statements.
- One pooled async engine (`core/db.py`, copied from OSCE). One session and one
  transaction per request (`get_session`); only `core/db.py` and `core/jobs.py`
  commit. Repositories may flush, services never.
- Slices declare SQLAlchemy mapped models in `models.py` (no `relationship()`).
  API schemas stay Pydantic.
- **Alembic owns `public` only.** `0001` is procrastinate's schema; `0002` is a
  snapshot of `backend/sql/001–089` with the Supabase-only parts removed (the
  `auth.users` foreign key, role grants, RLS); triggers and functions stay SQL.
  Autogenerate reflects only the default schema, so `auth`, `storage`, `realtime`,
  `extensions`, `vault` and the rest of Supabase's schemas are never diffed or touched.
- **The live database is adopted, not rebuilt** (`docs/runbooks/cutover.md`):
  `alembic upgrade 0001` (the queue, which Supabase lacks), `alembic stamp 0002`
  (already there, built by `backend/sql/`), `alembic upgrade head`. `0004` settles
  the one snapshot drift (the `users` comment) and revokes Supabase's default
  `anon`/`authenticated` grants on `public`, so nothing api creates is reachable
  through the Data API. `python -m app.migration adopt-auth` then copies the bcrypt
  hashes from `auth.users` into `users.password_hash` in the same database.
- `alembic check` runs in `make arch`, so the models and the schema cannot drift.
- Railway runs `alembic upgrade head` as the `api` service's pre-deploy command
  (a dashboard setting; `docs/runbooks/railway.md`).

## Consequences
- No data move. Supabase keeps the backups, PITR and the dashboard, and the
  baseline rollback is a DNS switch back. Leaving Supabase later is a `pg_dump` and
  a new `DATABASE_URL`; `app/migration`'s export/load/verify stays for that.
- Latency: Railway's only EU region is Amsterdam (`europe-west4`) and Supabase has
  no Amsterdam region, so each query crosses ~6–10 ms to London. The live baseline
  already makes the same trip to PostgREST, and api makes fewer round trips per
  page (one transaction, joins instead of sequential `.table()` calls).
- Connections are budgeted: every pooled connection is a pooler client, and the
  plan caps them (`docs/runbooks/railway.md`, "Database"; `DATABASE_POOL_SIZE` +
  `DATABASE_MAX_OVERFLOW` per process).
- Autogenerated migrations must be reviewed by hand; they miss constraint and
  index changes.
- Until cutover the baseline still migrates the live DB from `backend/sql/`. Any
  file added there must also land as an Alembic revision, and schema changes on
  the shared database happen only on cut-over day.
