# 0002 — Postgres on Railway through SQLAlchemy 2.0 and Alembic

Status: accepted (2026-09-26). Supersedes "keep supabase-py" (2026-09-25).
Source: OSCE Guide `platform-api` ADR 0013.

## Context
Every supabase-py `.table()` call is one HTTPS round trip to PostgREST. Pages that
make several sequential calls were measurably slow. PostgREST also cannot open a
multi-statement transaction or take a row lock, so atomic money writes needed
hand-written `.rpc()` functions. OSCE Guide already runs SQLAlchemy + Alembic on
psycopg 3; one stack across both projects was the deciding constraint.

## Decision
- Managed Postgres on Railway, reached over the private network with one pooled
  async engine (`core/db.py`, copied from OSCE).
- One session and one transaction per request (`get_session`); only `core/db.py`
  and `core/jobs.py` commit. Repositories may flush, services never.
- Slices declare SQLAlchemy mapped models in `models.py` (no `relationship()`).
  API schemas stay Pydantic.
- Alembic owns the schema. `0001` is procrastinate's schema; `0002` is a snapshot
  of `backend/sql/001–087` with the Supabase-only parts removed (the
  `auth.users` foreign key, role grants, RLS). Triggers and functions stay SQL.
- `alembic check` runs in `make arch`, so the models and the schema cannot drift.
  (OSCE's ADR promises this but its CI does not run it yet.)
- Railway runs `alembic upgrade head` as the `api` service's pre-deploy command
  (a dashboard setting; `docs/runbooks/railway.md`).

## Consequences
- Queries are ~1 ms on the private network, and real transactions and
  `SELECT … FOR UPDATE` replace `.rpc()`.
- Autogenerated migrations must be reviewed by hand; they miss constraint and
  index changes.
- Until cutover the baseline still migrates the live DB from `backend/sql/`. Any
  file added there must also land as an Alembic revision.
